# 2026-10-17: Formatting standard input

Editors format an unsaved buffer by piping it through the formatter (#106). chloro with no
source formats the current directory, so standard input needs a flag: `--stdin`.

## Current State

- **rustfmt with no file, observed with 1.9.0:** the formatted text on standard output and
  status 0; on a parse error nothing on standard output, the error under `<stdin>`, status 1;
  the configuration of the current directory; `--emit files` refused. `--check` prints the
  diff and exits with 0 even when the input needs formatting, which looks like a bug: chloro
  exits with 1 there, as for a file, and the compatibility page says so.
- **chloro:** `--stdin` reads the whole input, formats it under the configuration of the file
  `--stdin-filepath` names (it need not exist, as for a new buffer) or of the current
  directory, and writes the result; a parse error is rendered as for a file, under `<stdin>`
  or the given path. `--check` uses `is_unchanged`, so a buffer that differs only in its
  `\r\n` line endings passes. `--write`, sources and a lone `--stdin-filepath` are errors.
  Large input is split on threads as a large file is. Neither cache is read or written.
- **Editors.** The CLI guide gives settings for rust-analyzer (`overrideCommand`, which feeds
  the buffer on standard input), Zed (`{buffer_path}`), Helix (`%{buffer_name}`) and
  conform.nvim (`$FILENAME`). Experiment E21 found that a resident server saves little over
  a process per format, so this is the integration.
