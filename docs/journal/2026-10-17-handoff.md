## 1. Executive summary

chloro is a Rust formatter that reproduces `rustfmt --edition 2024` output byte for byte using
rust-analyzer's parser instead of rustc's. Before this programme it formatted the rust-analyzer
corpus at about 4.6 MB/s in process and matched rustfmt on 1219 of 1220 files. The programme set
out to make it substantially faster than rustfmt without changing any output, to reach 1220 of
1220, to support a second rustfmt version, and to leave a record a sceptical reviewer can check.

Thirty-one experiments ran (E1–E31), plus two fix branches (R2, R5) and six measurement runs
(M1–M6). Twenty experiments changed shipped code; nine ended with no shipped change (their
records say why); two were measurement or harness work only. Every merged change passed the
gates twice: once on its branch and again by the integrating session on the merged tree.

Readiness, in short (§11 has the detail): the code is in a releasable state as far as the
records can show. Output is identical to rustfmt on every corpus and option tested; the test
suite, fmt and clippy are clean; the one `unsafe` block has a safety argument and a randomised
test; the one new dependency (`bumpalo`) has no transitive dependencies; peak memory fell. The
items a release reviewer needs to look at are the opt-in unit cache, the cache's identity
record, the untested-in-release PGO workflow step, print-mode file order with several threads,
and the README badges. There is no test workflow on pull requests in this repository, so the
gates were run on the integration host, not by CI; pre-commit.ci passes on the PR head.

## 2. Goals, stated and implied

Stated at the start ([2026-10-14-autoresearch.md](2026-10-14-autoresearch.md) § What was asked):

1. Larger speedups against rustfmt than the 2–3x the project had, with correctness and
   conformance as hard constraints and the library's structure preserved.
2. Full conformance on the fixtures (1220 of 1220, not 1219).
3. Support for more than one rustfmt version.
4. Parallel investigation by agents on isolated branches, with every claim recorded so that a
   reviewer can check it without the conversation.
5. No edits to `docs/JOURNAL.md`.

Goals that became explicit during the work, and are now in the protocol:

- Exactness over speed: no change that alters any output on any corpus or option is kept,
  whatever it gains. Two kept changes were reverted during the programme for a single
  differing file before merge; none reached the branch.
- No `unsafe` without a written safety argument and a test; a safe version measured first
  where one exists (the hand-written arena of E25 was replaced by a `bumpalo` arena on this
  rule).
- No new runtime dependency without a measured reason (one was added, §5.5).
- A reported result is a claim until the integrating session reproduces it (every merge).
- Instruction counts are the primary metric because wall time on the shared 4-core host moves
  by 20–40% between windows; wall time is measured only on a quiet host and only as ratios
  within one window.
- From day 2: a change must not regress the registry sample while improving the fixture
  sample; a change under about 2 M instructions is judged on the per-file count.
- Negative results are recorded with the same detail as positive ones.

## 4. Timeline: what seemed promising when, and how that changed

The programme ran in four sessions. Each session started from a profile of the current code,
chose the levers the profile pointed at, ran them as parallel experiments, merged what passed
the gates, and measured the result on a quiet host. The direction changed three times as the
profile changed.

| session | what the profile said | what was expected to pay | what actually paid | what was closed |
|---|---|---|---|---|
| 1 (2026-10-14) | formatter logic 40% of instructions, parser and lexer 28%, allocator 15%, rowan tree operations and red-node creation a large share of the rest | process-level levers (a cache for unchanged files, parallel formatting of big files, a release build profile); replacing rowan's red/green tree with a flat array; the hot paths the profile named | all of them: cache 32x on an unchanged tree; big files 1.5–1.9x on four cores; fat LTO + PGO −24% instructions; the flat array −25% instructions and −43% allocations; 19 hot-path levers −19%; plus full conformance (R2) and rustfmt 1.8.0 (E8) | a CLI-only allocator (mimalloc: fewer instructions, no wall gain, 2–10x memory); `panic=abort`; `target-cpu=native`; splitting medium files across threads |
| overnight (14–15) | after the flat array: formatter still the largest share, parser 28%, allocator 12–15% | five theory records bounded the remaining levers before any code: the shared output sink (≤ 8.8–10.5%), a resident process (editor saves under 1 ms), width-model levers (up to 15–18% if an exactness proof existed), parser levers without a fork (P1–P8), scanner and string levers (≈ 12%) | the CLI's own waste (warm check 28 → 17 ms); PGO in the release workflow; eleven scanner and string levers −11.4%; three parser levers −7.1%; a dead speculative candidate removed −3.4%; an exact opt-in per-item cache | a replacement allocator (none met the memory rule); glibc tunables; the item cache as a default (its process-level gain is diluted by fixed costs) |
| 2 (2026-10-15) | formatter 50%+, parser 37–43%, allocator ≈ 12%; measurement found a third of cycles were not instruction-count effects (mispredicts, I-cache) | the ten tricks of the day-2 plan: code layout and branch shape, a dense memo table, a unit queue across files, the resident process, a bump arena, the shared sink, a width bound, a cliff hunt, the parser fork trigger, better instrumentation | the cliff hunt found a superlinear case (nested closures, exponent 3.6) and the width bound removed it (105 M → 5.7 M instructions at depth 16); the shared sink at one site −4.1%; six audit levers −2.4%; the memo depth gate −2.5%; the arena −1.6%; the harness became path-independent, per-file and two-sample | code layout and BOLT (I-cache misses are capacity misses; no wall gain); the chain-wide sink (costs more under glibc's realloc); the dense memo table (hit rate 3.2%); the unit queue (the schedule is already within 1% of the bound); the resident process for the CLI (the client process alone costs 2.1–2.3 ms) |
| 3 (2026-10-17) | parser 39–47% of instructions and the largest single component; the formatter's remaining attempts mostly decided by structure, not width | the lexer and token conversion (P2, P4) and `rustc_compat` inside the build (P7); an exact width model; the split file's own scheduling | the lexer front end −8.1% (fixtures) and −14.8% (registry), the largest single gain since session 1; one structural width rule −0.36% | the exact width model (everything a width can decide totals 0.28–0.39%); `rustc_compat` inside the build (the rules cost the same anywhere); the split file's scheduling (no idle tail exists once the trace sees item threads) |

Three beliefs changed during the programme, and the records show when:

1. **Wall time would follow instruction count.** It did, at about 0.6–1.0 of the count's
   movement on the crate rows, in every measurement from M2 to M6. The day-2 hypothesis that a
   third of the cycles were hidden from the count (branch mispredicts, instruction-cache misses)
   was measured (E22) and found not to be movable by layout: the misses are capacity misses on a
   49 KB hot footprint against a 32 KB L1 instruction cache, and BOLT cut them by 9% without a
   wall-time change.
2. **Scheduling was leaving cores idle.** M4's four-core figures suggested 2.7–3.7 of 4 cores
   busy. E23 rebuilt the schedule from thread CPU clocks and found it within 1% of the
   work-conserving bound; the gap was process start-up and run-to-run spread. M5 then reported
   a 22% tail on one crate; E29 showed that the release build's trace cannot see a split file's
   item threads and counts them as idle. There is no scheduling gain left to take.
3. **The parser was a fixed floor.** Session 1 treated the parser as given. The parse-floor
   record (overnight) listed eleven levers; five that need no fork are now done (E17: P1, P5,
   P8; E31: P2, P4), −7.1% and −8.1% on the fixture sample. The remaining three (P3, P6, P11)
   need a fork of `ra_ap_parser`; their bound is in §12.

## 5. What changed in the code, by area

Each area: what was done, what was tried and not kept, and what the records leave open.

### 5.1 The syntax tree (`chloro-core/src/cst/`)

- Done (E7b, session 1): rowan's red/green tree is replaced under the formatter by a flat
  preorder array of elements with `Copy` handles (`cst/mod.rs`) and a typed accessor layer
  generated from rust-analyzer's grammar (`cst/gen_ast.py`, `cst/rust.ungram`,
  `cst/generated.rs`, 501 accessors with the same names as `ra_ap_syntax`'s). Fragment trees
  (macro arguments) live in a run-lifetime arena (`typed-arena`). `rowan` and `ra_ap_syntax`
  became dev-dependencies, used only by the equality tests. Instructions −24.6%, heap
  allocations −43%, red nodes 0.
- Done (E17, overnight): the tree is built in one pass from the parser's output with the
  trivia attachment rules fused in (`steps_fused`), checked element by element against
  rust-analyzer's own interspersal over both corpora (0 mismatches on 35,338 file trees and
  639,895 fragment trees). E22 kept only the fused path and made it close nodes at their
  `Exit` event.
- Tried, superseded (E4): reading rowan's green tree directly on the hottest red-node creation
  paths (−6.4%) was overtaken by E7b, which removed red nodes altogether.
- Open: nothing in the tree itself. The parse floor record's §6 bounds the tree's remaining
  cost on the formatter side at a few percent of accessor overhead.

### 5.2 The parser front end (`chloro-core/src/cst/lex.rs`, `cst/mod.rs`)

- Done (E17): `in_trait` passed down instead of two backward parent searches (P8); macro
  arguments lexed and parsed once instead of twice (P5); the fused build (P1). −7.1% together.
- Done (E31, day 3): chloro converts `rustc_lexer`'s tokens to syntax kinds and builds the
  parser's `Input` in one pass of its own (P2), replacing rust-analyzer's `LexedStr::new` and
  `to_input`, and lexes the common tokens (whitespace, ASCII identifiers, one-byte punctuation,
  line comments) by a byte scan with the cursor for the rest (P4; the cursor still lexes 2.7–3.7%
  of tokens). Any text with a lexer error or a shebang/frontmatter goes to `LexedStr` as before,
  so error reporting is unchanged. −8.1% on the fixture sample, −14.8% on the registry sample.
  Exactness: `examples/lex_equality.rs` compares every token, every `Input` call and the
  parser's output with `LexedStr`'s over both corpora in two editions, 10,000 random texts and
  10,000 mutated fixtures (0 mismatches); debug builds cross-check every lexed text.
- Tried, rejected (E31): running `rustc_compat`'s checks inside the tree build (P7) costs the
  same as the separate walk (+0.42 M even inlined); the rules themselves are the cost.
- Not done (E10, E31): the three levers that need a fork of `ra_ap_parser` 0.0.307: sizing the
  parser's event vectors up front (P3), writing chloro's tree directly from the parser's events
  instead of through its `Output` (P6), and an own parser (P11). §12 has the bounds.

### 5.3 The formatter's hot paths (`chloro-core/src/formatter/`)

- Done (E3, session 1): 19 levers each with a test against the full computation: the comment
  scanner's character classes, the trailing-comma test, `filter_normal_code`, the line table,
  `node_text` copies, the memo result clone, path helpers. −19.0%.
- Done (E16, overnight): eleven scanner, list-gap and string-assembly levers, −11.4%. One of
  them is the only `unsafe` in chloro-core: an unaligned 16-byte SSE2 load in `comment.rs`,
  gated on the target feature, with a randomised test against the scalar search.
- Done (E19, day 2): six levers from a repeated-work audit: an if-else chain rendered in one
  buffer, use-tree segment comparison without clones, span and attribute facts decided from the
  first child, an early stop in `definitive_tactic`, macro token trees taken from the tree.
  −2.4% on the merged tree, −5.3% on the registry sample.
- Done (E20, day 2): `write_list_into` writes a list into the caller's buffer (one copy
  instead of two), the list's per-item scans are computed only where read, the chain's entry
  lists are sized up front. −4.1%.
- Done (E18, overnight): the chain's dead vertical candidate is skipped under a run-level
  guard (`RunState::whole_file`). −3.4%.
- Tried, rejected: a vectorised newline count (+4.47 M); per-byte lookahead in the comment
  scanner (+784 K); a literal-width cache (+1.75%, E18); the chain's rewrites in one growing
  buffer at every level (+2.0–2.5 M under glibc's `realloc`, E20); hand hot/cold function
  splits and a kind flag table (E22, no effect outside the spread).
- Open: the theory record's remaining string-assembly items (S6, S9, S14) were bounded under
  1% each and not taken.

### 5.4 Speculation control: memo and width (`context.rs`, `width.rs`, `closures.rs`)

- Done (E28): the rewrite memo stores results only from nesting depth 6 (`MEMO_MIN_DEPTH`),
  because the memo's hit rate is 3.2% on the fixtures and storing every result costs more than
  the hits save except on deep nesting. −2.5%.
- Done (E26): a lower bound on the width of any one-line rendering, summed from the tokens no
  formatting path removes, with a proof table per token class (`width.rs`); an attempt that must
  fit on one line is skipped when the bound exceeds the shape, at the closure-body and one-line
  `if`/`else` sites. −0.75% on the sample, and the nested-closure cliff is removed: a 2,000-byte
  file nested 16 deep went from 105.4 M to 5.7 M instructions (exponent 3.6 → 0.03 over depths
  8–16). The bound is checked against every actual rendering over both corpora, three option
  sets and the cliff files (`tests/width_bound.rs`).
- Done (E30): one structural rule: a closure body that renders a `match` arm is never one line
  (`never_one_line`, with the argument from rustfmt's `rewrite_match`). −0.36% per file.
- Tried, not built (E30): the exact one-line width `W(n)`: an instrumented replay of every
  one-line attempt put everything a width could decide at 0.28% (fixtures) and 0.39%
  (registry) of instructions, so the model was not written.
- Tried, rejected (E24): a dense side array for the memo instead of a hash map, four forms:
  best −0.16%; the lookup volume is too small for any layout to matter.
- Tried, rejected (E30): a second structural rule (a chain wider than `chain_width` is never one
  line) on a +10 K registry regression that the protocol's two-sample rule does not allow.

### 5.5 Allocation (`formatter/scratch.rs`, `Cargo.toml`)

- Done (E25): the module-local intermediates of chains, overflow's list items and path
  segments are allocated in a per-thread `bumpalo` arena lent to a closure, reset when the
  outermost borrower returns and at unit boundaries. −1.6% (fixtures), −0.7% (registry); peak
  memory 0.989–1.019x. `bumpalo` 3.20.3 is the one runtime dependency the programme added; it
  has no transitive dependencies. A hand-written arena with 13–16 `unsafe` blocks was built
  first, found Miri-clean, and replaced by the `bumpalo` version on the no-`unsafe` rule; it
  stays on branch `20261015-arena`.
- Measured, no change (E14): glibc's allocator is 13–16% of one thread's time. mimalloc,
  jemalloc and snmalloc were measured with memory-bounded settings; none kept peak memory
  within 1.2x of glibc on every workload with a wall-time gain outside the spread. The
  features `alloc-timing` and `alloc-{mimalloc,jemalloc,snmalloc}` remain in `chloro-core` as
  off-by-default instrumentation.
- Rejected (E9, E2): glibc malloc tunables (nothing outside the spread); mimalloc in the CLI
  (−12.4% instructions, no wall gain, 2–10x memory).

### 5.6 Parallel formatting and the CLI's scheduler (`formatter/parallel.rs`, `cli/orchestrate.rs`)

- Done (E1): files of 128 KiB and more have their top-level items formatted on all threads,
  with the text between items, reorder groups and skip regions kept sequential
  (`format_source_with_config_parallel`; `format_source` unchanged). The CLI hands files to one
  worker per core from a largest-first queue instead of static chunks; `--threads N`. Big files
  1.5–1.9x on four cores; crates 1.24–1.82x.
- Done (R5): the parallel replay checks every unit record and falls back to the sequential
  walk where a unit cannot be stitched; a worker panic keeps its payload;
  `tests/parallel_equivalence.rs` holds the two paths to identical output.
- Done (E23): `CHLORO_TRACE=<file>` makes the CLI write a per-file, per-worker timeline
  (`cli/trace.rs`); `benchmarks/schedule/` derives tails and idle core time and rebuilds the
  schedule from thread CPU clocks.
- Tried, rejected: a unit queue across files (E23, the schedule is within 1% of the bound);
  the split file's worker formatting units itself, and capping item threads at idle workers
  (E29, both exact, both reverted: no gain or a loss); splitting medium files (session 1,
  slower on crates).
- Open: for one very large file run alone, parsing its items in parallel was replayed at
  −43% of that file's time (E29); it does not help crate-level runs and was not built.

### 5.7 The CLI's caches (`cli/cache.rs`, `cli/unit_cache.rs`)

- Done (E6): the CLI records the BLAKE3 digest of every file it finds already formatted, in a
  file named by the digest of the chloro binary and of the `--config` options, under
  `--cache-dir`, `$CHLORO_CACHE_DIR` or the user cache directory. A later run hashes the files
  and formats none of them. `--no-cache` turns it off. Output and exit code are the same with
  and without it.

  digest read from an identity record (`<hex>.chloro-exe`: path, size, mtime, inode, device,
  ctime) instead of hashed from the 2 MB binary on every run. Warm `--check` of 1238 files 28
  → 17 ms.
- Done (R5): the cache file's 48-byte header carries its full key; the temporary file is
  created exclusively; stale temporaries are swept; the cache is opened before discovery.
- Done, opt-in (E15): `--unit-cache` also caches each formatted top-level item keyed by its
  text, the whole `Config` and the file's skip names (`.chloro-units`), so a changed file

## 10. How the work was run, and what the process learned

### 10.1 Method

- One hypothesis per experiment, stated with what would refute it, on its own branch
  (`YYYYMMDD-slug`) in its own worktree, run by one agent with a time box of 3–4 hours and a
  written brief: what to measure before writing code, the keep rule per commit, the gates, the
  record to write.
- The integrating session reproduced every gate on the merged tree before merging, one
  experiment per merge, and recorded the reproduced figures in the ledger. A reported result
  was treated as a claim until then. This caught one duplicate commit (E19 and E20 had made the
  same change) and one case where an agent's reproduction host differed.
- Negative results were written up with the same detail as positive ones; nine of the 31
  experiments ended with no shipped change and their records say what was measured.
- The protocol ([protocol.md](2026-10-14-autoresearch/protocol.md)) grew during the programme:
  a second instruction-count sample (day 2), a per-file count (day 2), a confirmation run from a
  clean build (day 2), a plateau rule (three experiments on one direction inside the noise
  close it).

### 10.2 Measurement lessons

- **Wall time on this host is not comparable across windows.** The same binary on the same
  bytes moved 20–40% between records (the start's in-process throughput read 3.68 to 5.09 MB/s).
  Every wall claim is a ratio inside one record; instruction counts carry between records.
- **The instruction count depended on path lengths.** Until E27, formatting the same sample
  from a directory with a longer name changed the count by up to 2.6 M through the heap's
  layout (glibc's size classes and the parser's vector growth). `profile.sh` now stages the
  binary and the sample under fixed-length paths, and reports a per-file count (each file in its
  own process) beside the whole-sample count; the difference is the layout term, and small
  changes are judged on the per-file figure.
- **A change selected on one sample can fit that sample.** The registry sample exists for this;
  it rejected one change (E30's second rule) that improved the fixture sample and regressed the
  registry sample.
- **The release build's trace cannot see a split file's item threads.** M5 reported a 22% idle
  tail on one crate; E29 showed the trace counted busy item threads as idle. A split file's
  tail has to be read from the patched (CPU-clock) build.
- **The memo's value is on deep nesting only.** Its hit rate on ordinary code is 3.2%; it exists
  for the cliffs (E28).

### 10.3 Process incidents

- The three day-3 agents were stopped by the account's weekly rate limit on the evening of
  10-15 before any had pushed; their worktrees were intact and they resumed on 10-17 and
  finished. The handoff records both times.
- The pre-commit.ci bot pushed three whitespace fixes to the branch during the programme; each
  time the next push was rebased onto it.
- The disk allowance filled twice from build trees and callgrind profiles; worktrees were
  removed after each merge.

### 10.4 External research

The owner ran a research brief through ChatGPT on 2026-10-15; the brief, the report, its own
summary and the follow-up message are stored verbatim in
[2026-10-15-external-research-brief/](2026-10-15-external-research-brief/) and assessed in
[2026-10-15-external-research-brief.md](2026-10-15-external-research-brief.md). Seven of its
suggestions were adopted into briefs and the protocol (the second sample, the additive term in
cliff fits, measuring imbalance first, the parse-only phase, the client's latency in the
daemon measurement, rollback as state, generation-stamped tables); its retrospective (§6 of that
entry) finds that every experiment it proposed has a ledger row, and that the parser fork is the
one proposal without one. Its claims about other projects (Biome, Lezer, Zig, Clang's BOLT run)
have not been checked against their sources by any session here.
