# Research protocol: gates, metrics, promotion

Operating procedure for the performance and conformance research on chloro. It is written
so that an engineer or a later session can run an experiment, judge it, and record it
without this conversation. The main entry is
[../2026-10-14-autoresearch.md](../2026-10-14-autoresearch.md); the experiment ledger is
[experiments.md](experiments.md).

## 1. Objective function

Four independent requirements. No score trades one against another.

1. **Conformance (hard gate).** Byte-for-byte equality with `rustfmt 1.9.0 --edition 2024`
   on the acceptance corpora. A candidate that changes any output that was identical to
   rustfmt's is rejected, whatever it gains in speed.
2. **Correctness (hard gate).** Workspace tests, clippy with `-D warnings`, `cargo fmt
   --check`; every output idempotent (`conform -i` reports 0 not idempotent); public API
   additive only.
3. **Performance (the quantity being maximised).** Instructions on the fixed sample
   (deterministic), in-process throughput, and process-level wall time against rustfmt,
   reported per workload. A regression on any workload is reported, not averaged away.
4. **Engineering integrity (hard gate).** No benchmark-specific semantics. No new `unsafe`
   without a safety argument and a test. No new dependency in `chloro-core` without a
   measured reason; CLI-only dependencies go behind the `cli` feature. The module-to-rustfmt
   map in `chloro-core/src/formatter.rs` stays readable: a change that makes a formatting
   decision untraceable to rustfmt's code is rejected.

## 2. Acceptance corpora and their reference

| corpus | files | reference | command |
|---|---|---|---|
| rust-analyzer fixtures, default config | 1220 | tracked snapshots `chloro-core/tests/conformance/snapshots/ra/*.rustfmt.rs`, generated by rustfmt 1.9.0 | `target/release/examples/conform -i` |
| rust-analyzer fixtures, 31 option values | 1022 accepted by rustfmt per value | rustfmt 1.9.0 run live | `target/release/examples/config_matrix -n 1220` |
| all 1238 fixture files, output hashes | 1238 | hashes recorded at the current best-known-good commit | `target/release/examples/bench --check <golden.tsv>` |
| cargo registry corpus (this container) | 20,570 `.rs` files in 577 crates under `~/.cargo/registry/src/index.crates.io-*/`, fetched by the manifest in [corpus/registry-manifest.toml](corpus/registry-manifest.toml) | rustfmt 1.9.0 run live | `target/release/examples/config_matrix --root ~/.cargo/registry/src -n 30000 default` |

The registry corpus is reproducible from the manifest and lockfile only to the extent that
crates.io still serves the same versions; its crate list with versions is recorded in
[corpus/registry-crates.txt](corpus/registry-crates.txt).

A "mismatch" is any byte difference between chloro's output and rustfmt's for the same
input and configuration, including a file one tool formats and the other returns unchanged.
Exit status is not compared (chloro's CLI and rustfmt's differ in reporting).

## 3. Performance metrics

| metric | tool | noise | use |
|---|---|---|---|
| instructions (`Ir`) on the 49-file sample (every 25th file of the sorted fixture list) | `benchmarks/profile.sh` (callgrind) | 0.0006% between runs since D1 (`fc90e53`); independent of where the sample and binary live since EXP-027 | primary metric for any change that does not add threads |
| `Ir` on the 49-file registry validation sample ([`benchmarks/samples/registry49.txt`](../../../benchmarks/samples/registry49.txt), EXP-027) | `benchmarks/profile.sh --sample-list benchmarks/samples/registry49.txt` | as above | validation: a lever selected on the fixture sample must not regress it |
| per-file `Ir`: each sample file in a process of its own, summed, net of an empty process (EXP-019, EXP-027) | `benchmarks/profile.sh --per-file` | a few K over 49 processes (minimum per file over `--runs 3`) | separates a lever's own work from the cross-file heap-layout term (EXP-020) |
| in-process throughput, 1238 fixtures, best of 5 | `target/release/examples/bench -n 5` | about ±4% between runs on this host | secondary; always run interleaved with the baseline binary |
| process-level wall time and peak RSS, per workload | `benchmarks/compare_rustfmt.sh` (hyperfine) | reported per run (min, mean, σ) | the numbers claimed against rustfmt |

A speedup claim needs:
- for single-threaded changes: lower `Ir` on the sample, and wall-clock ranges (min to max
  over at least 3 interleaved pairs of `bench -n 5`) that do not overlap;
- for changes that add parallelism: wall-clock only, hyperfine with at least 10 runs per
  command, interleaved, and the single-core figure (`taskset -c N`) reported next to it so
  per-core cost is visible;
- the same binaries measured in the same window on the same host. Numbers from different
  hosts or different windows are not compared (this container has moved hosts before and
  wall time moved 25%).

**Two samples (from E23 on).** Every record reports `Ir` on both samples, the fixture sample
(`benchmarks/profile.sh`) and the registry validation sample (`benchmarks/profile.sh
--sample-list benchmarks/samples/registry49.txt`), for the base and the candidate built
alike. A kept lever regresses neither: a candidate whose `Ir` rises on either sample by more
than the run-to-run spread (minimum of `--runs 3`) is not kept, whatever it gains on the
other. Levers were selected on the fixture sample alone up to E22, so a gain that does not
carry to the registry sample is fitted to the fixture sample's syntax mix, not a speedup
(the external research brief, §1.1). The registry sample's list is committed; a lever that
needs another sample adds one under `benchmarks/samples/` with its rule, it does not edit
an existing list.

## 4. Experiment procedure

1. Branch from the best-known-good commit: `git worktree add /home/user/wt/<slug> -b
   20261014-<slug>` (date prefix `YYYYMMDD-slug` for every research branch).
2. Write the hypothesis in [experiments.md](experiments.md) before measuring: mechanism,
   expected effect on which metric, risk, what result refutes it.
3. Implement the smallest change that tests the hypothesis. Performance changes change no
   output; conformance changes change exactly the targeted files.
4. Gates, in this order (cheap first):
   1. `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D
      warnings`, `cargo test --workspace --all-features`;
   2. `bench --check <golden.tsv>` — 0 of 1238 changed (or exactly the listed files for a
      conformance fix, after which the golden is re-recorded);
   3. `conform -i` — identical count not below the best-known-good, 0 not idempotent;
   4. `benchmarks/profile.sh` — `Ir` against the best-known-good, on both samples of §3
      from E23 on;
   5. `bench -n 5` interleaved with the best-known-good binary, 3 pairs;
   6. `config_matrix -n 1220` — no option value loses a file;
   7. registry corpus `config_matrix ... default` — identical count not below the
      best-known-good;
   8. `benchmarks/compare_rustfmt.sh` for process-level claims.
   A candidate that fails a hard gate stops there and is recorded as rejected with the
   failing gate.
5. Record the result in the ledger: kept, rejected or inconclusive, with the numbers and the
   commit. Negative results are recorded with the same detail as positive ones.
6. **Confirmation run, then merge.** Before merging, the integrator re-measures the branch
   head's instruction counts from a clean build (a fresh target directory, `cargo build
   --release -p chloro-core --examples`), on both samples of §3, with the base built the
   same way in the same window; the record's figures are claims until this run reproduces
   them within the run-to-run spread. A change of under about 2 M instructions on either
   sample is reported with the per-file figure beside the whole-sample one (`profile.sh
   --per-file --runs 3`): the cross-file heap-layout term moves the whole-sample count by
   −0.4 to +4.7 M with no change to the code it measures (EXP-019, EXP-020), so below that
   size a whole-sample difference alone does not separate a lever from a layout shift; where
   the two disagree, the per-file figure is the lever's own effect and the difference is
   recorded as layout. Then merge kept changes into the integration branch
   (`claude/chloro-perf-research-swarm-nrscj8`), one experiment per merge, re-run gates 1–3
   on the merged tree, then re-record the golden hashes and the `Ir` figure as the new
   best-known-good.

Two kept changes that each pass alone are measured together after the merge; an
interaction that loses either gain is recorded and the second change stays on its branch.

## 5. Best-known-good

The best-known-good (BKG) is a commit on the integration branch, named in
[experiments.md](experiments.md) with its `Ir`, `bench` throughput, `conform` count and
golden hash file. It changes only through step 6 above. A failed experiment never touches
it. The previous BKG stays reachable as a commit.

## 6. Parallel work

Independent hypotheses run on separate branches at the same time, by separate agents or
sessions. Rules:
- one hypothesis per branch; no branch touches the same hot path as another running
  branch unless the ledger says so;
- an agent reports its branch, commits, gate results and numbers; the integrator reruns
  gates 1–5 before merging — a reported result is a claim until reproduced;
- measurement runs on this 4-core host are pinned with `taskset` and labelled with the load
  at the time; multi-core wall-clock numbers taken while other agents run are provisional.

## 7. Plateau rule

After three consecutive experiments on one lever with gains inside the noise band, that
lever is closed in the ledger with its measured ceiling, and the next experiment comes from
a different row of the profile table, not from another variant of the same idea.

## 8. Record format for an experiment (ledger row plus optional file)

Row fields: id, branch, hypothesis (one sentence), mechanism, metric and expected size,
result (numbers), gates passed/failed, decision, commit, date.

An experiment with more than a page of evidence gets its own file
`experiments/EXP-NNN-slug.md` with: identity (branch, commits, base BKG, toolchain, flags),
hypothesis and falsification condition, exact commands, before/after tables per metric and
per workload, conformance results naming the corpora, interpretation, decision, follow-up.
